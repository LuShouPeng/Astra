# M5 已知局限与技术债务

> 本文档只记录 **M5 有意不解决** 的问题——即范围边界或复杂度决定应留给后续里程碑的取舍。
>
> 注意：原先草稿中列出的"方案设计缺陷"（如 beforeunload 不可靠）与"低成本防御"（如 buffer 上限、
> 工作目录冲突检测、saveSnapshot 串行化、exit 非 0 抓 stderr）**已纳入 M5 实施范围**，不在本文档，
> 详见 [`PLAN_M5.md`](../../PLAN_M5.md) 的"M5 内解决项"。

## 1. stdout 累积——语义割裂（500ms 超时的固有代价）

**场景**：Agent 输出一段代码块，中间停顿超过 500ms（模型推理慢、等待输入），会被拆成多条 Timeline 事件。

````
Event 1: "Here's the solution:\n```python"
-- 600ms 停顿 --
Event 2: "def foo():\n  return 42"
````

**影响**：Timeline 显示不连贯；跨事件的 markdown 代码块渲染可能断开。
**为何 M5 不解决**：这是 500ms 累积策略的固有权衡，彻底解决需识别代码块/语义边界（复杂），或改用 CLI 结构化输出（依赖 M7 适配器）。
**后续方向**：M6 加"合并相邻 agent_message"，或识别 ` ``` ` 边界动态延长超时。
**严重度**：🟡 中等（影响可读性，不丢数据）

## 2. resume 功能缺失（M5 mock）

> **M7 已解决（Codex 范围）**：`resumeLiveSession` 现读取持久化日志，并以原工作目录调用 `codex exec resume --last`。Claude/Gemini 不伪装为可恢复，UI 仅对符合条件的 Codex live Session 显示 Resume。

M5 不实现真实 resume，`resumeLiveSession` 抛错或提示"暂不支持"。

### 2.1 用户预期落空

**场景**：session 列表有历史会话，点"恢复"发现不可用。
**影响**：困惑；工作流断裂（须新建 session 重述问题）。
**缓解**：UI 明确标注"恢复执行功能开发中"，提供"查看历史日志"作为替代。
**严重度**：🟡 中等（有替代方案）

### 2.2 上下文丢失（限制核心场景）

**场景**：Agent 执行到一半，用户关闭应用；重开后无法接续（Agent 不记得已完成的工作）。
**影响**：**M5 只适合短任务（几分钟内完成），不适合多轮/长时间运行场景**。
**为何 M5 不解决**：resume 语义依赖各 provider CLI 能力（`--resume`/`--continue`/不支持），需 M7 三 provider 数据齐备后设计通用方案 + 降级策略。
**严重度**：🔴 高（限制使用场景，但属明确的分阶段取舍）

### 2.3 与 demo session 行为不一致

**问题**：demo session 能在已完成会话上"继续"（`applyFollowUp`），live session 不能（进程已退出）。
**影响**：UX 不一致，用户困惑。
**缓解**：UI 区分 live/demo，或 demo 也禁用已完成会话的 follow-up 以保持一致。
**严重度**：🟡 中等

## 3. stderr 不进 Timeline（仅落日志）——部分缓解后的残留

> M5 **已实施**"exit 非 0 时抓取 stderr 末尾若干行塞入 StatusEvent"（见 PLAN 的 C 类），
> 因此"完全看不到错误"的最严重情况已缓解。以下是残留局限。

### 3.1 运行中 stderr 不可见

**场景**：Agent 卡住不动，stderr 有 warning（rate limit、network timeout），但进程未退出，Timeline 看不到。
**影响**：高级用户无法实时定位问题（须打开日志文件）。
**为何 M5 不解决**：实时 stderr 展示需专门 UI（诊断面板），超出 M5 范围。
**后续方向**：M6 加折叠式"诊断面板"实时显示 stderr。
**严重度**：🟡 中等（有 workaround：查日志文件）

### 3.2 快照重现性缺失

**场景**：用户分享 session 快照排查问题时，stderr 不在快照里（在独立日志），信息不完整。
**缓解**：后续加"导出完整会话"（快照 + 日志打包）。
**严重度**：🟢 低（工作流问题）

## 4. TimelineEvent 转换——复杂输出与操作审计

### 4.1 复杂输出乱码

**场景**：Agent 输出进度条（`\r` 覆盖）、ANSI 彩色、对齐表格。
**影响**：Timeline 显示乱码或语义错误（进度条变 100 行重复文本）。
**为何 M5 不解决**：需 ANSI 过滤 + `\r` 合并 + 进度事件建模，工作量集中在特定 CLI（编译器/下载器），留待适配器阶段统一处理。
**后续方向**：M7 加 `strip-ansi` + `\r` 合并 +（可选）`progress` 事件类型。
**严重度**：🟡 中等（影响特定 CLI）

### 4.2 命令执行隐式

**问题**：Agent 的真实命令（`git commit`、`npm test`）埋在 stdout，Timeline 无独立 `CommandEvent`。
**影响**：用户不知道 Agent 执行了什么操作；无法单独审计命令历史。
**为何 M5 不解决**：可靠提取命令依赖 CLI 结构化输出（如 `--json`），属 M7 适配器职责；正则匹配 stdout 不可靠。
**后续方向**：M6/M7 解析结构化输出生成独立 `CommandEvent`。
**严重度**：🔴 高（核心可观测性缺失，但依赖上游能力）

### 4.3 文件变更未关联

**问题**：Agent 修改文件，Timeline 无实时 `FileChangeEvent`（只能事后查 git diff）。
**影响**：Timeline 是"对话记录"，非"操作审计"。
**为何 M5 不解决**：与 M5 目标（对话生命周期）不冲突；实时文件监听属 M6 项目关联范畴。
**严重度**：🟡 中等（功能缺口，不阻塞 M5）

## 5. 日志文件管理——无轮转、无清理

### 5.1 日志体积无上限

**场景**：长时间运行的 Agent（几小时批量任务）产生 GB 级日志。
**影响**：磁盘占用；`session_log_read` 解析慢；"查看日志"前端卡死。
**为何 M5 不解决**：轮转机制（切分文件、倒序读）是独立特性，长时间运行才暴露。
**后续方向**：M6 加日志轮转（每 10MB 切分 `{id}.log.N`）+ `session_log_read` 倒序读取。
**严重度**：🟡 中等（长任务必现）

### 5.2 无过期清理

**问题**：旧 session 日志永久保留，即使快照里已删除该 session。
**影响**：磁盘浪费；敏感输出未清理（隐私）。
**后续方向**：加"清理 N 天前日志"，或快照删除时同步删日志。
**严重度**：🟢 低（长期运行问题）

## 6. 跨平台兼容性未验证

M5 在 Windows 开发，假设 Linux/macOS 兼容（Rust + Tauri 跨平台）。

### 6.1 进程管理差异

**风险**：M3 `kill_tree` 在 Windows 用 `taskkill /T`（递归），Unix 用 `kill -TERM`（不递归杀子树）。
**影响**：Linux 上孤儿进程风险更高。
**为何 M5 不解决**：M3 已实现跨平台分支，但无 Linux/macOS 真机环境验证；属"未验证"而非"未实现"。
**后续方向**：M8 回归阶段在 Linux/macOS 真机验证；Unix 侧考虑用 process group（`setsid` + `kill -TERM -pgid`）递归杀。
**严重度**：🟡 中等（需真机验证）

### 6.2 路径与配置目录

**风险**：`~/.astra/sessions/` 依赖 Tauri `app.path().home_dir()` 跨平台返回值差异（M5 最终未引入 `dirs` crate，直接用 home 目录拼 `.astra/sessions`）。
**缓解**：Rust `std::path` 自动处理分隔符（M3 `safe_directory` 已验证 Windows）。
**后续方向**：M8 真机验证 macOS/Linux 路径。
**严重度**：🟢 低（标准库保证）

## 7. 并发 session——资源争抢

> M5 **已实施** 工作目录冲突检测（同一目录已有 running session 则拒绝新建，见 PLAN C 类），
> 因此"两个 session 改同一目录导致脏数据"的最严重情况已阻断。以下是残留局限。

### 7.1 CPU/内存争抢

**场景**：用户在不同目录同时启动多个 Agent，每个都编译大项目。
**影响**：机器卡死；进程 OOM。
**为何 M5 不解决**：并发数限制/优先级队列属资源调度特性，且合理并发是正常用法，不宜过早限制。
**后续方向**：M6 加可配置并发上限或排队机制。
**严重度**：🟡 中等（依赖用户自律）

## 8. 测试覆盖盲区

### 8.1 流事件真实时序

**问题**：单测用 fake adapter 同步触发事件，真实场景是异步高频流。
**影响**：真机可能暴露单测无法覆盖的时序问题。
**缓解**：M5 手动测试覆盖"高频输出"场景（如 `yes | head -1000`）。
**严重度**：🟡 中等（真机压测补充）

### 8.2 快照序列化性能

**问题**：单测 snapshot 很小，真实用户可能 100+ session、1000+ event。
**影响**：`saveSnapshot` 在大数据下可能慢。
**为何 M5 不解决**：性能优化需真实数据规模驱动，渐进暴露。
**后续方向**：M8 加大 snapshot 性能测试。
**严重度**：🟢 低
